# Дизайн: Генератор збалансованих скриптів для Blood on the Clocktower

**Дата:** 2026-06-10
**Статус:** Затверджено до планування реалізації

## 1. Огляд

Веб-застосунок, який за заданим **концептом** генерує **збалансовані кастомні скрипти** для Blood on the Clocktower. Користувач описує ідею (тему, кількість гравців, складність, обов'язкові/виключені ролі), а застосунок за допомогою Claude складає тематично цілісний і механічно збалансований скрипт із пулу офіційних та власних (homebrew) персонажів.

Це **особистий інструмент**: працює локально, використовує власний Anthropic API-ключ користувача, без акаунтів та авторизації.

### Що це НЕ робить (межі обсягу / YAGNI)
- Не призначає ролі конкретним гравцям на партію (генеруємо *скрипт*, не *розсадку*).
- Не керує живою грою (не Storyteller-tool, не grimoire).
- Без багатокористувацькості, акаунтів, спільного хостингу (можливе майбутнє розширення, але не зараз).
- Без бази даних win-rate реальних ігор (оцінка балансу — через LLM).

## 2. Ключові рішення

| Рішення | Вибір | Обґрунтування |
|---|---|---|
| Що генерувати | Кастомний скрипт (набір ролей) | Класичне розуміння «збалансованого сценарію» |
| Пул персонажів | Офіційні видання + homebrew | Гнучкість; homebrew оцінюється через LLM |
| Модель генерації | Керована за концептом | Користувач задає ідею + обмеження |
| Оцінка балансу | LLM-аналіз (Claude) | Покриває homebrew, враховує тему й нюанси |
| Стратегія движка | Генерація → Оцінка → Доопрацювання (цикл) | Найкращий компроміс якість/вартість для особистого інструмента |
| Платформа | Веб-застосунок | Доступність, зручність ділитися результатом |
| Масштаб | Особистий інструмент | Свій API-ключ, мінімум інфраструктури, без auth |
| Вихід | Офіційний JSON + PDF-роздавалка з іконками | Імпорт у clocktower.online / botc.app + друкована роздавалка |

## 3. Архітектура

Три рівні:

### ① Фронтенд — браузерний SPA (React + Vite + TypeScript)
Усе, що бачить користувач; стан зберігається локально.
- **Форма концепту** — тема, кількість гравців, складність, must-include/exclude, вибір видань у пулі.
- **Прогрес генерації** — візуалізація кроків циклу.
- **Перегляд результату** — скрипт за командами з іконками, розбір балансу, експорт.
- **Менеджер хоумбрю** — додавання/редагування власних ролей.
- **Експорт** — кнопки JSON / PDF.

### ② Бекенд — легкий локальний Node-сервер
Тримає API-ключ поза браузером, оркеструє движок, роздає фронтенд.
- `POST /generate` — запускає цикл Генерація → Оцінка → Доопрацювання.
- **Движок балансу** — промпти, валідація, скоринг (розділ 5).
- **Експорт-модуль** — форматер офіційного JSON + рендер PDF.

**Чому потрібен бекенд:** виклик Anthropic API напряму з браузера розкрив би ключ і впирався б у CORS. Маленький локальний Node-сервер тримає ключ у себе та проксує виклики; він же роздає фронтенд. Користувач запускає одну команду й відкриває `localhost`.

### ③ Дані та зовнішнє
- **База персонажів** — вбудований JSON офіційних ролей.
- **Сховище хоумбрю** — локальний JSON / `localStorage`.
- **Anthropic API** (зовнішнє) — Claude для генерації та оцінки.

## 4. Модель даних персонажів

### Офіційні персонажі
Вбудований JSON, зібраний із канонічного датасету ролей спільноти (того, що використовують clocktower.online / офіційний Script Tool). Схема запису:

```
id          — офіційний ідентифікатор (напр. "fortuneteller")
name        — назва
team        — townsfolk | outsider | minion | demon | traveller | fabled
edition     — tb | bmr | snv | experimental
ability     — текст здібності (головне для LLM-оцінки)
tags        — опційні механічні теги (info, protection, death, disruption…)
              для фільтрації та зіставлення з концептом
jinxes      — список взаємодій { with: id, reason }
setup       — чи змінює склад гри (напр. Baron додає Outsider'ів)
icon        — посилання/шлях на офіційну іконку ролі (для PDF)
```

### Homebrew-персонажі
Та сама схема; `name`/`team`/`ability` задає користувач, `id` генерується. Іконка — завантажена користувачем або плейсхолдер. В офіційному JSON-форматі лягають як inline-об'єкти (формат це підтримує), тож згенерований скрипт із homebrew лишається імпортованим.

## 5. Движок генерації — цикл «Генерація → Оцінка → Доопрацювання»

Послідовність після `POST /generate` (кроки з Claude позначено **[AI]**):

1. **Збір пулу** *(бекенд)* — фільтр персонажів за обраними виданнями + homebrew; примусово лишаємо must-include, прибираємо exclude; додаємо концепт, кількість гравців, складність.
2. **Генерація кандидата [AI]** — системний промпт = експертиза дизайну скриптів + евристики балансу; на вхід пул ролей і обмеження; вихід — **структурований JSON** (за схемою): обрані id за командами + коротке обґрунтування концепту.
3. **Валідація** *(бекенд)* — усі id існують; склад адекватний (≈13 Townsfolk / 4 Outsiders / 4 Minions / 1+ Demon, або відповідні розміри Teensyville); must-include присутні, exclude відсутні, є хоча б один Demon. Структурні помилки → авто-запит на виправлення (див. розділ 6).
4. **Оцінка балансу [AI]** — окремий прохід-критик. Бали за осями: щільність інформації, відчуття вінрейту добро/зло, надмірність ролей, вироджені комбо, навантаження джинксів, складність vs ціль, відповідність концепту. Повертає **числові бали + текстову критику + конкретні запропоновані заміни**.
5. **Рішення про доопрацювання** *(бекенд)* — якщо загальний бал ≥ порогу **або** досягнуто ліміт ітерацій → фіналізація; інакше → крок 2 із зауваженнями критика («виправ слабкі місця, збережи вдале»). **Максимум 2 ітерації.**
6. **Фіналізація** *(бекенд)* — фінальний об'єкт скрипту + розбір балансу (з останньої оцінки) для екрана; підготовка артефактів експорту (офіційний JSON + PDF-роздавалка з іконками).

**Чому два окремі виклики (генерація і оцінка):** модель-критик, що дивиться на готовий скрипт «свіжим оком», ловить проблеми балансу надійніше, ніж та сама модель, що водночас створює і хвалить власний результат.

**Параметри, що налаштовуються:** поріг балансу та ліміт ітерацій (стартові: поріг ~8/10, ліміт 2) виносяться в конфіг.

## 6. Обробка помилок

| Випадок | Поведінка |
|---|---|
| Немає/невірний API-ключ | Чітке повідомлення на старті + посилання, де взяти ключ |
| Claude повернув некоректний JSON / неіснуючі id | Валідація + авто-ремонт (запит на виправлення 1–2 рази), потім зрозуміла помилка |
| Rate limit / збій API | Ретрай з експоненційним backoff, статус на екрані |
| Жорсткі обмеження несумісні (must-include конфліктують, пул замалий) | Виявляємо **до** виклику Claude, пояснюємо причину |
| Баланс не дотягнув до порогу після 2 ітерацій | Віддаємо найкращого кандидата з **попередженням**, а не помилкою |
| Таймаут / мережа | М'яке повідомлення + повтор |
| Битий homebrew | Валідація при введенні в менеджері |

## 7. Тестування

Пірамідою:
- **Unit:** логіка валідації (склад скрипту, існування id, must/exclude), форматер офіційного JSON, фільтрація пулу, генерація PDF.
- **Движок із мок-відповідями Claude:** детерміновано перевіряємо цикл — спрацювання доопрацювання, поріг, ліміт ітерацій, шлях авто-ремонту. Без реальних викликів API.
- **Golden-тест схеми:** експортований JSON чисто імпортується у формат офіційного Script Tool.
- **Frontend:** компонентні тести форми та перегляду результату.
- **Light E2E (опційно, вручну):** один реальний наскрізний прогін.

## 8. Користувацький потік (підсумок)

1. Користувач відкриває `localhost`, (за потреби) додає API-ключ та homebrew-ролі.
2. Заповнює форму концепту: тема, гравці, складність, must/exclude, видання.
3. Тисне «Згенерувати» → бачить прогрес циклу.
4. Отримує скрипт за командами + розбір балансу з оцінками.
5. За бажанням: **↻ Доопрацювати** (ще ітерація з приміткою) або **⇄ Інший варіант**.
6. Експортує **JSON** (імпорт у BotC-додатки) та/або **PDF-роздавалку** з іконками.

## 9. Орієнтовний стек

- **Фронтенд:** React + Vite + TypeScript.
- **Бекенд:** Node (легкий HTTP-сервер), офіційний Anthropic SDK для виклику Claude (структурований вивід для генерації/оцінки).
- **PDF:** бібліотека рендеру PDF на боці сервера, офіційні іконки ролей.
- **Дані:** статичний JSON офіційних ролей у репозиторії; homebrew у `localStorage`/локальному файлі.
- **Модель:** актуальний Claude (напр. `claude-sonnet-4-6` для генерації; вибір моделі — конфіг).
